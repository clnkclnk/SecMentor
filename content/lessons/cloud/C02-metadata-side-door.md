## 钩子

云主机像住进房东配好家具的厢房：屋里有一面**魔镜**（元数据服务），一问就告诉你「你是谁、你的临时腰牌在哪」。  
本来只给厢房里的人用。若应用有 SSRF，或容器网络没隔好，外人可能借你的嘴去问魔镜——于是**临时凭证溜出门**。  
这课建立直觉：元数据不是玄学端口号，是「身份的侧门」。

（停：等学员说「继续」）

## 片 1 · 魔镜在哪、一般回答什么

各云实现细节不同，心智模型一致：

- 实例内部可访问一个链路本地地址（常听说的 `169.254.169.254` 一类）  
- 返回：实例角色、临时密钥、用户数据等  
- **拿到角色临时密钥 ≈ 在权限边界内变成那台机器的身份**

你不需要死背每个路径；要记住：**能从应用打到元数据，就可能完成「身份窃取」**。

（停：等学员说「继续」）

## 片 2 · 和 Web 漏洞怎么拼在一起

经典拼图（练武场故事）：

1. 应用有 SSRF / 不安全的 URL 拉取  
2. 攻击者诱导服务器去访问元数据地址  
3. 响应里出现临时凭证  
4. 用凭证调云 API（仍须在授权评估范围内验证）

防御侧常听到的 **IMDSv2**（或各云等价加固）：要求会话头、更难点从 SSRF 一把梭——说明厂商也知道这扇侧门危险。

（停：等学员说「继续」）

## 片 3 · Hunter 汇报时怎么说才专业

少说：「我打了 metadata。」  
多说：

- 入口漏洞是什么（例如 SSRF 参数）  
- 是否触达元数据 / 是否拿到何种凭证（类型、是否临时）  
- 该身份**策略上**能碰哪些资源（blast radius）  
- 修复建议：修入口 + 强制加固元数据 + 角色最小权限

## 今日微任务

二选一：

**A（有自己的云主机）**：在**本机**按官方文档查元数据（或开启 IMDSv2 前后对比文档步骤），用自己的话写：默认能拿到哪类信息；你做了哪项加固。  
**B（无云主机）**：读一篇公开的「SSRF to cloud metadata」案例分析（合法文章），用 6 行复盘：入口 → 元数据 → 凭证 → 影响 → 修复。

禁止对未授权目标探测 `169.254.169.254`。
